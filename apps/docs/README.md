# Kiln docs

The public docs site for Kiln: Fumadocs on Next.js, built with `@mitcsutt/kiln-ui` itself ([ADR 0009](../../docs/adr/0009-docs-and-storybook.md), [ADR 0019](../../docs/adr/0019-docs-site.md)). It's a private app: never published, and not deployed by this repository. Its intended home is `kiln.mitchellsutton.com`.

```sh
pnpm --filter @mitcsutt/kiln-docs dev      # http://localhost:3000
pnpm --filter @mitcsutt/kiln-docs build    # the deployable Next.js build
pnpm check:links                           # build, serve, and fail on any broken internal link
```

## Where things live

```
content/docs/         MDX pages and meta.json files: the sidebar tree (docs/tree.json at the root)
examples/             one file per live example, named by its path: <Example name="ui/actions/button/hierarchy" />
scripts/              generate-api.ts, generate-tokens.ts, generate-examples.ts, examples-files.ts, extract-example.ts, generate-design-rules.ts, check-links.ts
src/app/              routes: pages, /api/search, /llms.txt, /llms-full.txt, /docs/<page>.md
src/components/       the site chrome, MDX components, foundations specimens
src/skills/           the agent skills kiln-ui and kiln-forms ship, built from these pages
src/styles/harbour.css  the custom theme the Theming guide builds
```

## Writing a page

- A page is MDX with `title`, `description` and `exports` (the public exports it documents) in its frontmatter. `src/test/tree.test.ts` fails when a component, field, layout, hook or function has no page, when a Storybook title has no page, or when the sidebar groups differ from `docs/tree.json`.
- A live example is a named export of an examples file beside the code it documents ([ADR 0025](../../docs/adr/0025-colocated-examples.md)): `<Example of="Button" name="Hierarchy" />` is the `Hierarchy` export of `Button.examples.tsx`, and `Usage` when `name` is left out. A guide's examples file under `packages/<pkg>/src/docs/` is named by its path: `<Example of="forms/getting-started/schemas" />`. The examples still in `examples/`, one `'use client'` file per example with a default export, are shown with `<Example name="ui/actions/button/hierarchy" />` until they move. `src/test/tree.test.ts` fails when a tag names an export, file or example that doesn't exist.
- The page renders the example and shows its source underneath, from the same file, so the two can't disagree. The source shown is the export's slice: its declaration plus the top-level helpers and imports it uses. Examples are typechecked and linted, and each slice is typechecked on its own from `.generated/examples/`.
- `<ApiTable of="ButtonProps" />` renders props from the package types; `<ApiSignature of="useFormStatus" />` renders a function's signature; `<ComponentTokens of="Card" />` lists the tokens a component's CSS Module declares. All three are generated by the scripts, never written by hand.
- Every page is also served as Markdown at its URL plus `.md`, with examples as code and API tables as Markdown tables, and listed in `/llms.txt`.
- The agent skills in `packages/ui/skills` and `packages/forms/skills` are that same Markdown ([ADR 0011](../../docs/adr/0011-ai-tooling.md)). `src/skills/manifest.ts` lists the pages each skill is built from. After changing one, run `pnpm generate:skills` from the root; `src/skills/skills.test.ts` fails while a skill differs from its pages.
- Every `ts`, `tsx` and `js` code block compiles against the packages, under the rules `intent validate` applies to the skills: `src/test/code-blocks.test.ts` fails otherwise, with live examples and API signatures included. A fragment may use names it doesn't declare (`form`, `save`), but it must parse and type-check: wrap sibling JSX in a fragment, and call hooks inside a component.
- UI › Foundations › Design rules is generated from DESIGN.md §1 and §2 by `scripts/generate-design-rules.ts`. Edit DESIGN.md, not the page.

Write as the rest of the repo does: [DESIGN.md](../../DESIGN.md)'s copy rules apply (sentence case, specific invented content, no lorem ipsum).
